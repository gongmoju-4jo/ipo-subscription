# S3 프롬프트 원문

LLM에 준 프롬프트 원문이다. 응답 원문은 `s3-response.md`, 사용한 LLM과 절차는 `README.md`.

---

공모주 청약 서비스의 부하 테스트용 가상 사용자 데이터를 만들어 줘.

## 서비스
- 증권사 한 곳의 공모주 청약 시스템이야. 투자자가 앱에서 청약 버튼을 누르면 `POST /api/v1/subscriptions`가 호출되고, 서버는 요청을 Kafka에 넣은 뒤 202를 응답해. 실제 접수(저장, 증거금 인출)는 뒤에서 비동기로 처리돼
- 요청 본문: `{ "requestId": UUID, "ipoId": UUID, "accountId": UUID, "requestedQuantity": 정수 }`
  - `requestId`는 클라이언트가 청약 1건마다 만드는 값이야. 같은 `requestId`로 다시 보내면 서버는 같은 청약으로 보고 새로 만들지 않아 (재전송 멱등)
- 한 사람은 한 종목에 유효한 청약 1건만 가질 수 있어. 같은 사람이 다른 계좌로 같은 종목을 또 청약하면 늦게 처리된 쪽이 `ALREADY_SUBSCRIBED`로 거절돼 (이중청약 방지, DB 조건부 유니크 `UNIQUE(ipo_id, user_id) WHERE status NOT IN ('REJECTED','CANCELLED')`)
- 청약 수량은 모든 요청이 10주로 같아

## 시나리오 (S3): 청약 마감일 오전, 앱 응답이 느려지는 시간대
- 가상 사용자 대부분은 청약 버튼을 한 번 누르고 끝나
- 일부는 응답이 늦다고 느껴 같은 청약을 다시 보내 (같은 `requestId` 재전송). 응답을 받은 뒤 다시 누르는 경우와, 다른 기기나 탭에서 거의 동시에 다시 보내는 경우가 섞여
- 일부는 본인 명의의 다른 계좌로 같은 종목을 한 번 더 청약해 (같은 증권사 안 이중청약 시도)
- 두 행동을 모두 하는 사람도 소수 있을 수 있어

## 부하 도구와 맞춰야 하는 조건
- 요청은 정확히 1,000건이야. k6가 가상 사용자(VU) 100명으로 각자 10번씩 순서대로 보내고, 100명은 1초에 걸쳐 차례로 시작해
- CSV의 i번째 행(0부터)이 i번째 요청이야. i번째 행은 VU `i // 10 + 1`이 `i % 10`번째로 보내
  - 그래서 바로 다음 행(i+1)은 같은 VU가 앞 요청의 응답을 받은 뒤 보내는 요청이고 (블록 경계를 넘지 않을 때), 10행 뒤(i+10)는 옆 VU가 거의 같은 시각에 보내는 요청이야
- `vuser`는 투자자 번호(0부터)야. 실제 회원, 계좌, 토큰은 부하 도구가 이 번호로 따로 붙여
- 재전송, 다른 계좌 청약은 같은 투자자의 첫 청약보다 뒤 행에 와야 해
- 모든 투자자의 첫 청약(`NORMAL`)은 정확히 1번씩이고, 재전송(`RESEND`)과 다른 계좌 청약(`SECOND_ACCOUNT`)은 투자자당 최대 1번씩이야
- 첫 청약을 하는 투자자는 0번부터 빈 번호 없이 이어져야 해

## 출력
- 열: `vuser,persona,action`
  - `persona`: 투자자 유형을 짧은 한국어로 (쉼표 없이)
  - `action`: `NORMAL`, `RESEND`, `SECOND_ACCOUNT` 중 하나
- 각 행동의 비율과 배치를 정한 이유를 먼저 짧게 설명해 줘
- 1,000행의 개수, 순서 조건이 정확해야 해서, CSV를 만드는 Python 코드(표준 라이브러리만, 고정 시드라 다시 실행해도 같은 결과)를 같이 줘
