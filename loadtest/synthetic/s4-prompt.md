# S4 프롬프트 원문

LLM에 준 프롬프트 원문이다. 응답 원문은 `s4-response.md`, 사용한 LLM과 절차는 `README.md`.

---

공모주 청약 서비스의 부하 테스트용 가상 사용자 데이터를 만들어 줘.

## 서비스
- 증권사 한 곳의 공모주 청약 시스템이야. 투자자가 앱에서 청약 버튼을 누르면 `POST /api/v1/subscriptions`가 호출되고, 서버는 요청을 Kafka에 넣은 뒤 202를 응답해. 실제 접수는 뒤에서 비동기로 처리돼
- 증거금률이 100%라서 청약 금액(공모가 x 청약 수량) 전액을 예수금에서 청약증거금으로 옮겨야 청약이 확정돼. 예수금이 모자라면 계좌 서비스가 인출을 거절하고 청약은 `INSUFFICIENT_BALANCE`로 거절돼
- 이번 테스트 종목의 공모가는 15,000원, 모든 요청의 청약 수량은 10주라서 청약 1건에 150,000원이 필요해
- 예수금은 계좌 개설 뒤 입금 API로 한 번 넣어. 입금액은 1원 이상의 정수(원)야

## 시나리오 (S4): 청약 첫날 오전, 예수금을 제대로 준비하지 못한 투자자가 섞인 상황
- 가상 사용자 대부분은 예수금을 충분히 넣어 두고 청약해
- 일부는 청약 금액보다 적은 예수금으로 청약해 (입금을 잊었거나, 일부만 넣었거나, 필요한 금액을 잘못 계산한 경우 등)
- 투자자 1명은 청약 1건만 보내

## 부하 도구와 맞춰야 하는 조건
- 요청은 정확히 1,000건이고 투자자도 1,000명(`vuser` 0~999, 각 1번)이야. k6가 가상 사용자(VU) 100명으로 각자 10번씩 순서대로 보내고, CSV의 i번째 행(0부터)이 i번째 요청이야
- 같은 데이터로 같은 투자자들이 4번 청약해 (종목은 매번 새것, 예수금은 처음 한 번만 넣음). 확정된 청약은 150,000원씩 예수금에서 빠져
  - 그래서 4번 모두 결과가 같도록, 입금액은 **150,000원 미만(매번 거절)** 이거나 **600,000원(150,000원 x 4) 이상(매번 확정)** 이어야 해. 그 사이 금액은 쓰지 마
- 예수금이 부족한 투자자가 특정 구간에 몰리지 않고 요청 순서 전체에 흩어져야 해

## 출력
- 열: `vuser,persona,deposit`
  - `persona`: 투자자 유형을 짧은 한국어로 (쉼표 없이)
  - `deposit`: 입금액 (원, 정수)
- 부족한 투자자의 비율과 금액 분포를 정한 이유를 먼저 짧게 설명해 줘
- 1,000행의 개수, 금액 조건이 정확해야 해서, CSV를 만드는 Python 코드(표준 라이브러리만, 고정 시드라 다시 실행해도 같은 결과)를 같이 줘
